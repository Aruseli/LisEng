## 1. Два SRS для словаря: экспонента 2^n + SM-2

**Проблема:**  
У тебя фактически две разные системы планирования для одного и того же контента:

- «Экспонента» `2^n` (cap 30) → своя логика mastery/difficulty.  
- SM-2 → своя логика интервалов и EF.  

При этом:

- Дата повторения берётся из SM-2.  
- Difficulty / mastery — из экспоненты.  
- Критерий mastered для глаголов не совпадает с «mastered» в SM-2.

**Последствия:**

- Непредсказуемое поведение: карточка может быть «mastered» по одной метрике и «требует повторения» по другой.  
- Сложно объяснить пользователю (и себе) логику повторений.  
- Трудно сравнивать эффективность методов и делать A/B.

**Что делать:**

- Выбрать **один основной SRS** для словаря:
  - Либо SM-2 (или FSRS), либо экспоненту, но не оба одновременно.  
- Если экспонента нужна как «упрощённый режим», сделать её:
  - либо **альтернативным режимом** на уровне пользователя/курса;  
  - либо внутренним эвристическим слоем, который **не хранит собственное расписание**, а только влияет на параметры основного SRS (например, начальный EF или difficulty).

## 2. Дублирование SM-2-обвязки в review API и lesson completion

**Проблема:**  
Логика обновления SM-2 (расчёт интервалов, EF, повторений) дублируется в двух местах:

- review API;  
- lesson completion.

**Последствия:**

- Высокий риск рассинхрона: в одном месте обновили формулу/правила, в другом забыли.  
- Сложнее тестировать и менять алгоритм.

**Решение:**

- Выделить **единый сервис/модуль SRS** (например, `SrsScheduler`):
  - Вход: `card_id, rating, delta_t, current_state`.  
  - Выход: `new_state, next_interval, next_review_date`.  
- Review API и lesson completion должны **только вызывать** этот модуль, а не реализовывать логику сами.

Это также упростит будущий переход на FSRS: меняешь один модуль, а не два-три места.

## 3. `words_learned` растёт на каждый correct swipe

**Проблема:**  
Метрика `words_learned` считается как количество правильных свайпов, а не как количество **уникальных новых слов**, доведённых до mastery.

**Последствия:**

- Метрика сильно завышена и не отражает реального прогресса.  
- Геймификация (лидерборды, стрики, достижения) строится на шумных данных.

**Решение:**

- Переопределить `words_learned` как:
  - количество уникальных слов, достигших **определённого порога mastery** (например, N успешных повторений + интервал ≥ X дней).  
- Текущий счётчик правильных свайпов можно оставить как вспомогательную метрику (например, `total_correct_answers`), но не называть её «words learned».

## 4. Speaking accuracy → `accuracy_writing`

**Проблема:**  
Метрика speaking accuracy записывается в поле `accuracy_writing`, то есть смешиваются разные навыки.

**Последствия:**

- Невозможно корректно анализировать прогресс по speaking vs writing.  
- Insights/рекомендации будут неадекватны.

**Решение:**

- Разделить метрики:
  - `accuracy_speaking`;  
  - `accuracy_writing`;  
  - возможно, `accuracy_listening`, `accuracy_reading`.  
- В прогресс-инсайтах явно показывать разбивку по навыкам.

***

## 5. `accuracy_threshold` без данных = выполнен

**Проблема:**  
Если нет данных по accuracy, условие `accuracy >= threshold` считается выполненным по умолчанию. Это позволяет «пройти» этап без реальных измерений.

**Последствия:**

- Пользователь может формально завершить модуль, не показав нужный уровень навыка.  
- Метрики эффективности курса становятся бессмысленными.

**Решение:**

- Требовать **минимальное количество измерений** (N попыток) до проверки порога.  
- Если данных недостаточно — этап считается «в процессе», а не «выполненным».  
- Либо явно помечать такие кейсы как «completed without accuracy data» и не считать их полноценным завершением.

## 6. MethodologyAdvisor ↔ ProgressInsights: обнуление `sm2Schedule.dueToday[]`

**Проблема:**  
Адаптер обнуляет `sm2Schedule.dueToday[]`, из-за чего blueprint’ы `sm2_due` из snapshot-пути становятся пустыми. Плюс есть два разных типа `SnapshotInsights`.

**Последствия:**

- Insights получают некорректные данные о том, сколько карточек должно быть повторено сегодня.  
- Рекомендации и адаптация методологии строятся на искажённой картине.

**Решение:**

- Убрать побочный эффект «обнуления» из адаптера.  
- Сделать **один канонический источник истины** для расписания SM-2:
  - либо live-данные;  
  - либо snapshot, но тогда адаптер должен работать с ним, а не ломать.  
- Унифицировать тип `SnapshotInsights`: оставить один, второй либо удалить, либо явно пометить как legacy.

## 7. Insights читают `vocabulary_cards.ease_factor`, а EF живёт в `active_recall_sessions`

**Проблема:**  
Мастери/диффиколти в insights опираются на поле `ease_factor` в таблице `vocabulary_cards`, но реальное состояние EF хранится в сессиях активного повторения.

**Последствия:**

- Mastery/difficult words в инсайтах ненадёжны.  
- Рекомендации «повтори сложные слова» могут указывать не на те карточки.

**Решение:**

- Определить **единое место хранения EF и состояния карточки**:
  - либо в `vocabulary_cards` (каноническое состояние);  
  - либо в `active_recall_sessions`, но тогда insights должны читать оттуда (или из агрегированного представления).  
- Убрать дублирование: EF не должен жить в двух местах с разной актуальностью.

***

## 8. Две таблицы стрика: `streaks` vs `user_streaks`

**Проблема:**  
Две сущности для одного концепта → риск рассинхрона и путаницы.

**Решение:**

- Оставить одну таблицу (скорее всего, `user_streaks`, если она более полная).  
- Вторую либо:
  - удалить;  
  - либо превратить в read-only денормализованное представление (и чётко документировать).

***

## 9. Магические числа по всему коду

Перечисленные:  
- EF min 1.3 / start 2.5;  
- интервалы 1/6;  
- quality time 2/5с;  
- verb mastered 5 reps + 30 дней;  
- daily pack 3–5;  
- Kumon consecutive 3;  
- Shu readiness 80/85%;  
- streak % 7.

**Проблема:**  
Размазанные по коду константы трудно менять, тестировать и объяснять.

**Решение:**

- Вынести все в **единый конфиг** (например, `SrsConfig`, `MethodologyConfig`):
  - с понятными именами: `SM2_EF_MIN`, `SM2_EF_DEFAULT`, `SM2_INITIAL_INTERVALS`, `QUALITY_FAST_THRESHOLD_MS`, `VERB_MASTERED_REPS`, `VERB_MASTERED_MIN_INTERVAL_DAYS`, и т.д.  
- Добавить комментарии/документацию, откуда взяты значения (эмпирика, литература, эксперименты).  
- Где возможно — сделать настраиваемыми на уровне курса/пользователя.

## 10. Upsert задач по `type` — нельзя два vocabulary в день из разных источников

**Проблема:**  
Если задача уникальна по `type + date`, то нельзя иметь два разных vocabulary-задания в один день (например, из разных курсов/источников).

**Последствия:**

- Ограничивает гибкость методологии и эксперименты.  
- Может приводить к потере данных или перезаписи задач.

**Решение:**

- Расширить уникальный ключ:
  - например, `(user_id, type, source_id, date)` или добавить отдельный `task_group`.  
- Либо явно разделить типы задач: `vocabulary_courseA`, `vocabulary_courseB`, если они методологически различаются.

***

## 11. Init SM-2 с quality 0 сразу портит EF

**Проблема:**  
Если при инициализации карточки сразу прогоняется «виртуальное» повторение с quality 0, EF падает (~1.7) ещё до реальной попытки.

**Последствия:**

- Новые карточки стартуют с заниженным EF → неоптимальные интервалы с самого начала.  
- Искажается статистика и ощущение «справедливости» алгоритма.

**Решение:**

- Инициализировать карточку **без симуляции повторений**:
  - `repetitions = 0`, `interval = 0`, `EF = default` (2.5).  
- Первый реальный ответ пользователя — первая точка для обновления SM-2.  
- Если нужна «прогревочная» логика, делать её явной и документированной, а не скрытым сайд-эффектом при создании.

## Приоритизация

Если расставлять по влиянию на продукт:

1. **Единый SRS для словаря** (п.1) + **централизация логики SM-2** (п.2).  
2. **Исправление метрик**: `words_learned`, speaking/writing accuracy, accuracy_threshold (п.3–5).  
3. **Консистентность данных для insights**: EF/mastery, dueToday, snapshot (п.6–7).  
4. **Уборка дублирования сущностей**: streaks, типы snapshot (п.8).  
5. **Конфигурируемость и чистота кода**: магические числа, upsert-логика, init EF (п.9–11).
